01新老流程对比

upstream 已同时保留两条路径：args == nullptr 进入旧流程；args != nullptr 进入 Driver Device 内存快照流程。新流程先检查驱动能力，备份时记录 Runtime/Driver API 版本，恢复时校验版本。

变化集中在 Device 内存内容的保存与回填。旧流程由 Runtime 收集地址并搬运到 Host；新流程由 Driver 按内存快照标识处理。模型 SQ 备份、参数池传输映射恢复、模型和图恢复仍保留。

② 流控制5 项

一个流可以包含多个任务，流控制任务本身也是其中的一项任务。执行到这项任务时，根据其控制动作，改变流的激活状态或后续执行位置。各个任务仍属于各自的流。

Stream：Runtime 管理的任务流。SQ（Submission Queue）：任务提交队列。SQ 存放提交给设备调度器的 SQE（Submission Queue Entry，任务提交描述条目）；Stream 记录关联的 SQ ID。

参数池申请点

内部参数通常从 H2DCopyMgr 的 BufferAllocator 取 entry。池初始化或扩容时申请整块 Device 内存；random-size 路径直接按大小申请。任务的参数指针可以指向整块内存中的一个 entry 或偏移位置。

  • 普通池：H2DCopyMgr::MallocBuffer。
  • PCIe BAR 池：H2DCopyMgr::MallocPcieBarBuffer。
  • UB 池：H2DCopyMgr::MallocUbBuffer。
  • random-size：H2DCopyMgr::AllocDevMem(size)。

这些申请路径最终调用 Driver::DevMemAllocWithBackupFlag()。

Host 落点：申请总长度为 opTotalHostMemSize_ 的连续数组，保存到 opBackUpAddrs_；按地址列表顺序，以 offset 逐块拼接：

MemCopySync(hostAddr + offset, size, addr, size, RT_MEMCPY_DEVICE_TO_HOST);
offset += size;

参数地址在 KernelLaunch 构造任务时进入 comm.args 等字段。参数块内部保存的张量地址不会触发递归遍历。opVirtualAddrs_ 使用 vector 逐项追加，同一地址可以出现多次。

03旧恢复流程及恢复内容

  • 入口与前置状态：旧入口向 SnapShotProcessRestore() 传入 nullptr，外层要求状态为 BACKED_UP。
  • 回调顺序：先执行 RESTORE_PRE，完成下列恢复后，再执行 RESTORE_POST。
  • 结束状态：状态回到 LOCKED，随后由调用方执行 Unlock。

顺序依赖：设备和页表恢复后才能使用原 Device 地址；Stream 恢复后才能下发配置和内存拷贝任务；Module 与参数内容回填后，继续恢复参数池传输映射、模型 SQ 和图。

全局阶段：先完成所有 Device 的设备恢复与资源恢复，再恢复 Module。

  1. SnapShotDeviceRestore：重开设备并恢复页表

    • 重新打开设备：逐个调用 Device::ReOpen()，关闭主机侧设备连接，重新拉起 AICPU executor（设备侧算子执行进程），打开设备并更新 SSID。
    • 恢复地址访问基础：调用 ProcessResRestore(0)，由 Driver（驱动）恢复进程资源和页表信息，使原设备地址重新可用。

  2. SnapShotResourceRestore：恢复运行资源与配置

    • 恢复任务流：Context 先执行 StreamsTaskClean()，再执行 StreamsRestore()，恢复默认流、创建的流及适用的控制流。
    • 重新申请同步标识：逐设备重新申请 Event（事件）、Notify（通知）、CountNotify（计数通知）的 ID。
    • 恢复运行配置：ResourceRestore() 恢复错误记录的环形缓冲区，按平台准备 Dcache（数据缓存）栈，重新发送 AICPU topic 版本、超时配置并启动 Dcache lock 操作。
    • 重置事件扩展池：执行 EventExpandingPoolRestore()，重置池中的缓冲区。

  3. RestoreModule：回填 Program / Module 内存

    • 读取与写回：遍历 moduleBackupList_，把每个 hostAddr 的 memSize 字节写回记录的 devAddr。
    • 恢复内容：算子二进制加载区域、SO（Shared Object，共享库）名称、函数名称，以及 Module 的 AICPU 名称区域。
    • 拷贝路径与属性：kernel 内存池中的地址走 BinaryPoolMemCopySync()，其余走 BinaryMemCopySync()；携带节点的 readonly 属性。

逐 Device 阶段：对一个 Device 按下面顺序全部完成，再处理下一个 Device。

  1. OpMemoryRestore：回填模型任务引用的内存

    • 读取与写回：按 opVirtualAddrs_ 的顺序和长度，从 opBackUpAddrs_ + offset 取主机侧备份，写回记录的设备地址。
    • 恢复内容：第 2.1 节的参数块、MIX/FFTS 执行上下文描述、func-call 指令程序及 tiling 相关数据。
    • 下发并等待完成：通过当前 Context 的控制 SQ stream 执行 MemcopyAsync(..., HOST_TO_DEVICE)，最后调用 Synchronize() 等待回填完成。

  2. ArgsPoolRestore：恢复主机与设备参数缓冲区的搬运地址关系

    • 处理范围：UmaArgLoader 的普通、super、max、random 参数池。
    • DMA 全称与作用：Direct Memory Access，直接内存访问，由专用硬件负责把主机侧参数数据搬到设备侧。
    • 更新搬运地址信息：PCIe DMA 策略下，针对已有的主机侧和设备侧缓冲区调用 MemConvertAddr()，重新获取搬运所需的源地址、目标地址及相关信息，更新到 cpyAddr.dmaAddr，供后续参数搬运使用。
    • UB 策略分支：使用 UB 策略的这些参数池也会重新获取主机侧和设备侧的内存段描述；UB 的含义及描述内容见下一步。

  3. UbArgsPoolRestore：恢复 UB 参数池的内存段访问资料

    • UB 全称与含义：本节 UB 指 Unified Bus，统一总线。它是一套硬件互联方案，提供主机与设备之间的连接通路和通信规则：发送方按规定格式发出数据，接收方按同一规则识别并送到目标位置。
    • 参数数据的路径：主机参数缓冲区（一块存放参数的内存） → UB 互联通路 → 设备参数缓冲区。
    • 与 DMA 的区别：UB 提供部件之间的数据通信通路与规则；DMA 是由专用硬件执行内存搬运的机制。
    • 处理范围：启用 UB 连接时，处理 UbArgLoader 的普通和 super 参数池。
    • 内存段描述：segment（内存段）是一段内存范围；这里的描述保存 UB 传输访问这段内存所需的信息。
    • 更新两侧访问资料：对已有缓冲区调用 GetMemTsegInfo()，按主机地址、设备地址和长度重新获取两侧描述，刷新 hostTsegInfo 与 devTsegInfo，使后续 UB 参数传输使用当前有效的访问资料。

  4. ModelRestore：重建模型与 SQ 任务

    • 处理范围：遍历该设备的活跃 Context 及 TS executor 模型；Software SQ capture 模型和 auto-split SQ 模型在这条遍历中跳过。
    • 执行模型重建：对每个符合条件的模型调用 Model::ReBuild()，依次执行：
    1. ReSetup()：重新申请 model ID；写入 Device 的 model ID、endGraph、activeEntryStream；重新申请模型 stream ID。
    2. ResetForRestore()：释放并清空旧的 streamInfo、aicpuTaskInfo、queueInfo 以及模型 func-call 相关内存和状态，为重新完成模型加载做准备。
    3. ReBindStreams()：将非 AICPU stream 重新绑定到模型，保留 head stream 标识。
    4. SinkSqTasksRestore()：收集模型 stream 的 SQ ID，调用 Driver SqRestore() 恢复已备份的下沉队列任务。
    5. CheckRestoredSqStatus()：检查 SQ 未启用且 head 为 0，tail 的最终状态在后续加载完成流程校验。
    6. ModelLoadCompleteByStream() / LoadCompleteByStream()：按设备特性重新完成模型加载，建立执行所需信息。
    7. UpdateSnapShotSqe()：逐 stream 修正恢复后的任务信息。Device SQ 路径更新 StreamActive 的 func-call、适用的 2D memcpy DMA 信息，以及 StreamSwitch、ModelTaskUpdate 的 SQE；Software SQ 路径更新 Host SQE。

  5. SnapShotAclGraphRestore：恢复 Software SQ capture 图资源

    • 通信资源：按需重置 UB Jetty。
    • 图模型资源：对已 capture ready 且启用 Software SQ 的 CaptureModel，重新申请 model ID 并调用 RestoreForSoftwareSq()。
    • 队列资源池：最后恢复设备的 SqCqPool。

  6. RestoreAiCpuKernelInfo：回填 ArgLoader 名称缓存

    • 处理范围：遍历 UmaArgLoader::soNameMap_ 和 kernelNameMap_。
    • 数据来源与写回：把主机侧名称缓存保存的字符串写回对应的设备地址。

  7. AICPU timeout 清理：重置超时监控状态

    • 清除超时状态：执行 ClearAicpuTimeoutState()。
    • 关闭旧监控：非 PC 构建还调用 TryCloseAicpuMonitor()，为后续运行重新建立监控状态做准备。

  8. BatchLoadCustomAicpuSo：重新加载自定义 SO

    • 适用设备：备份时记录存在自定义 AICPU 进程的设备才进入该步骤。
    • 加载数据来源：筛选已加载的 CPU Program，从主机侧 Program::Data()、LoadSize() 和 GetSoName() 构造临时设备缓冲区。
    • 加载与回收：执行 batchLoadsoFrombuf，同步后释放临时内存。

  9. SetAicpuDfxForRestore：重新建立 printf DFX

    • 适用条件：设备支持 AICPU DFX（维测功能），且 printf 已就绪。
    • 恢复打印支持：执行 ReInitAicpuPrintfMem()、SetupAicpuPrintfDfx()，恢复 printf 所需的内存、地址配置及处理线程。
